# Owner API

Контракт текущей реализации. Базовый URL: `http://localhost:8080/api/v1/owners`. JSON; `{id}` — UUID владельца. Связанный модуль: [Car API](car-service.md).

## Операции

| Метод | Путь относительно базового | Действие | Успех |
| --- | --- | --- | --- |
| POST | `/` | Создать владельца | `201` + OwnerResponse |
| GET | `/` | Поиск активных владельцев | `200` + OwnerPageResponse |
| GET | `/{id}` | Получить активного владельца | `200` + OwnerResponse |
| PATCH | `/{id}` | Обновить активного владельца | `200` + OwnerResponse |
| DELETE | `/{id}` | Мягко удалить | `204`, без тела |
| DELETE | `/{id}/admin` | Физически удалить | `204`, без тела |
| PATCH | `/{id}/restore` | Восстановить | `204`, без тела |

В строках `/` используется сам базовый URL без завершающего слеша. `/admin` не обеспечивает проверку роли: авторизация пока не реализована.

## Данные и правила

При создании все поля обязательны. В PATCH отсутствие поля и `null` сохраняют прежнее значение; `{}` допустим. Связи с автомобилями через Owner PATCH не меняются.

| Поле | Ограничения переданного значения |
| --- | --- |
| `fullName` | 2–100 символов, не только пробелы |
| `phone` | 11 цифр, первая `7`; без `+`, пробелов и дефисов |
| `email` | Непустой адрес, проходящий `@Email` |

| Сценарий | Поведение |
| --- | --- |
| Soft delete | Запись сохраняется, исчезает из поиска; GET/PATCH по ID дают `404` |
| Любое удаление при наличии автомобилей | `409`, в том числе при наличии мягко удалённых автомобилей |
| Повторный soft delete / restore активной записи | `409` |
| Hard delete | Разрешён для активной или мягко удалённой записи без автомобилей; восстановление невозможно |
| Несуществующий ID | `404` |

## Поиск

Query-параметры необязательны, разные фильтры объединяются через `AND`.

| Параметр | Правило |
| --- | --- |
| `fullName` | Часть ФИО без учёта регистра; края обрезаются, пустой фильтр игнорируется; `%`, `_`, `\` — обычные символы |
| `owners` | Точное совпадение с одним из ФИО; пример: `owners=Alice&owners=Bob` |
| `phone`, `email` | Точное совпадение; валидация формата как выше |
| `createdFrom`, `createdTo` | Даты создания `YYYY-MM-DD`, не в будущем |
| `updatedFrom`, `updatedTo` | Даты обновления `YYYY-MM-DD`, не в будущем |
| `page` | С нуля; отсутствующее или отрицательное значение заменяется на `0` |
| `size` | 1–100; отсутствующее или выходящее за диапазон значение заменяется на `20` |
| `sortBy` | `fullName`, `phone`, `email`, `updatedAt`; отсутствующее/пустое → `fullName` |
| `direction` | `asc`/`desc`, регистр неважен; отсутствующее/пустое → `asc` |

Границы дат независимы, включают целые дни в часовом поясе сервера. Обратный диапазон даёт пустой результат, а не ошибку. Неподдерживаемая сортировка — `400`.

## Ответы

| Модель | Поля |
| --- | --- |
| OwnerResponse | `id`, `fullName`, `phone`, `email`, `cars`, `createdAt`, `updatedAt` |
| Элемент `cars` | `id`, `vin`, `regNumber`, `manufacturer`, `model` |
| OwnerPageResponse | `owners` (массив OwnerResponse), `page`, `size`, `totalElements`, `totalPages` |

Даты владельца: `HH:mm - dd.MM.yyyy`, например `14:30 - 30.09.2026`, без смещения часового пояса. Вложенный `cars` сейчас не фильтрует мягко удалённые автомобили. Поиск без совпадений: `200`, `owners: []`, `totalElements: 0`, `totalPages: 0`. `size` — запрошенный размер страницы, `totalElements` — количество всех совпадений.

## Примеры

Тело `POST /api/v1/owners` с `Content-Type: application/json`:

```json
{"fullName":"Алексей Петров","phone":"79991234567","email":"alex@example.com"}
```

Тело `PATCH /api/v1/owners/{id}` — меняет телефон, сохраняет email:

```json
{"phone":"79991234568","email":null}
```

Поиск: `GET /api/v1/owners?phone=79991234568&sortBy=updatedAt&direction=desc&page=0&size=10`.

## Ошибки

| Статус | Причины |
| --- | --- |
| `400` | Невалидные поля, сортировка, JSON, UUID или тип параметра |
| `404` | Владелец отсутствует либо мягко удалён при GET/PATCH |
| `409` | Нарушение правил удаления/восстановления из таблицы выше |
| `500` | Ошибка БД или другая внутренняя ошибка |

Доменные исключения и `MethodArgumentNotValidException` возвращают ErrorDto, например:

```json
{"statusCode":409,"message":"Нельзя удалить владельца, пока за ним закреплены автомобили"}
```

Для некорректного JSON/UUID и необработанных ошибок формат может отличаться. Ошибки валидации пока содержат технический текст `e.getMessage()`; единой обработки всех ошибок БД нет. DTO-валидация запускается через `@Valid` в контроллере, не при прямом вызове сервиса.
